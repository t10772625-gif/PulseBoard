### B. Role architecture review

**Removed / added / renamed (migration 21 as written):**
- `Owner` — no longer assigned (enum value stays, CHECK constraints forbid it). Existing
  Owner members become `Admin`.
- `Admin` — becomes the top role, always full access (matrix can't restrict it).
- `Sub Admin`, `Member`, `Viewer` — unchanged defaults.
- **Client Viewer** — does **not** exist in the database today (clients use share links); not
  added by migration 21.

**"Creator" technically:** not a role. `workspaces.created_by` = the auth user id of whoever the
sign-up trigger created the workspace for (backfilled from today's Owner). `is_creator(ws)` =
`created_by = auth.uid()`.

**Protection in DB:**
- `members: change` / `members: remove` USING/WITH CHECK: the row's `user_id` must not be
  `workspaces.created_by` (nobody, including the creator, can change or remove that row).
- Trigger `workspace_members_no_self_role` blocks any self role change.
- `test_set_plan` requires `is_creator(ws)` and role Admin.

**Who can do what (migration 21 as written):**

| Action | Old (today, migrations ≤ 20) | Proposed (21) |
| ------ | ---------------------------- | ------------- |
| Change plan (test switch) | Owner | Creator (must be Admin) |
| Billing (real) | not built | not built — intended creator-only |
| Delete workspace | not built (no feature) | not built; only indirectly via `delete_my_account()` when the creator is the sole member |
| Transfer ownership | not built | not built (creator can't even leave) |
| Rename workspace | Owner | any Admin |
| Grant / change / remove Admin | Owner only | any Admin (except the creator's row) |
| Edit matrix rows | Owner: all except Owner (incl. Admin row); Admin: Sub Admin/Member/Viewer | Admin: Sub Admin/Member/Viewer; Admin row fixed full |
| Manage integrations | `automation.manage` (Owner/Admin by default) | same; Slack/Discord also `automation.manage`; AI opt-in Admin-only |
| Custom domain / branding / SLA | browser only | Admin (workspace_settings policy) |
| Recover a workspace | DB owner (SQL editor) | same — no in-app recovery |
| Change own role | blocked in UI; DB allowed (with `member.manage`) | blocked in DB (trigger) |

**Default permission matrix (pages / actions):** Owner (old) and Admin = all 12 pages + all 12
actions. Sub Admin = 9 pages, 10 actions (no `member.manage`, `automation.manage`; pages
without automations/integrations/settings). Member = 8 pages, 7 actions. Viewer = 4 pages,
0 actions (enforced). Old difference: Owner could restrict Admin's row; proposed: can't.

**If the creator deletes the account:** blocked while other members exist (`delete_my_account`
raises). If they are the only member: the workspace and everything in it is deleted.
**If the creator deactivates:** `profiles.deactivated_at` set; their membership and creator
protection remain; nobody else can change the plan; there is no transfer or recovery path in
the app. This is an open gap.

**Invitations / existing memberships:** invites with role Owner → Admin (live DB: 0 invites);
the one live Owner member → Admin + `created_by`.

**Why Owner "cannot remain":** it can. Removing it was the user's 2026-10-02 request, not a
technical need. The user's current stated preference is **Owner, Admin, Member, Viewer, Client
Viewer**, with Sub Admin later becoming a scoped board/department admin. That direction would
mean: keep migrations 14–20 as they are, **discard migration 21's role parts**, keep only
non-role pieces if wanted (sign-up profile fields, self-role-change trigger), and design Client
Viewer separately (share-link-based today).

**Rollback:** see A (21). Live data impact today is one row, but the code in `repo.ts`,
`permissions.ts`, the team/permissions/plan pages and i18n already assume the new model and
would need to be reverted together.
