### Details

#### F-2026-10-01-14 — Comment reply regression

- **Severity:** Medium (functional regression; denied too much, no data exposure)
- **Introduced by:** `20261001001860_protect_comment_authorship.sql`, applied 2026-10-01
- **Root cause:** ambiguous / unqualified `parent_id` binding in the
  `comments: create` policy. In `select 1 from public.comments pc where pc.id = parent_id`
  the bare `parent_id` bound to the inner alias `pc`, so Postgres stored
  `pc.id = pc.parent_id` (never true) → every reply rejected.
- **Why it was missed:** the pre-apply test only checked that the expression
  compiles against real columns, not which row each column binds to, and no
  allow / deny case with a real reply was run.
- **Fix:** `20261001001890_fix_comment_reply_parent_check.sql` — all new-row
  columns written as `comments.<column>`. Applied 2026-10-01.
- **Status:** VERIFIED FIXED AT DB LEVEL — BROWSER VERIFICATION PENDING.
  Stored policy expression corrected and DB scenario test passed (6 comment
  cases incl. reply allowed); browser authenticated test pending.
- **Prevention:** all policy / function row references must be qualified
  (`<table>.<column>` for the new / outer row) and tested with real allow / deny

### ADR-001 — Tenant isolation and RLS strategy

**Context.** PulseBoard is multi-tenant; every board, task, comment, file and
setting belongs to one workspace. The browser talks to Supabase directly with
the user's JWT, so the database is the security boundary.

**Decision.**
- Every public table has RLS enabled and a `workspace_id` (or a parent that can't cross tenants).
- Policies use SECURITY DEFINER helpers that only describe the **caller**:
  `member_role_in(ws)`, `is_member(ws)`, `can_edit(ws)`, `is_admin(ws)`,
  `has_permission(ws, perm)` (role matrix in `role_permissions`).
- The signed-in role `authenticated` gets only the table / column privileges each
  table needs (migration `15_api-grants`); `anon` gets no table access. Public
  share pages go through `get_shared(token)` only.
- INSERT / UPDATE policies also check that every referenced parent (task,
  project, parent comment, storage folder) is in the **same** workspace as the row.
- Row references inside policy sub-queries are always qualified
  (`<table>.<column>`) and tested with allow / deny cases (lesson from F-2026-10-01-14).

**Consequences.** Client-supplied ids are only requests; RLS decides. New tables
need RLS + explicit grants + same-workspace parent checks in their own migration.

**Enforced in.** `supabase/migrations/01_…`–`18_security-hardening`.
**Verification.** DB-level (V-2026-10-01-02/03); real signed-in tests pending (TEST-ROLE-001, TEST-XTENANT-001).

### ADR-002 — No direct `workspace_members` INSERT; invitation acceptance is the trusted path

**Context.** `members: add` allowed inserting any user id; every user owns a
workspace, so anyone could attach a stranger and read their email via the
teammates profile policy (F-2026-10-01-02).

**Decision.** `authenticated` has no INSERT on `workspace_members` and there is
no INSERT policy. Memberships are created only by trusted server-side code:
`handle_new_user()` (SECURITY DEFINER, owner `postgres`) on sign-up — joining a
pre-approved `workspace_invites` row, or creating the user's own workspace as Owner.
Role changes / removals stay under `members: change` / `members: remove`
(only Owner grants or changes Admin).

**Consequences.** Adding an existing user to another workspace needs a future
explicit accept-invitation flow (reviewed SECURITY DEFINER RPC or server route
with consent), not a client insert.

**Enforced in.** `…1850_remove_direct_member_insert.sql`, `16_workspace-invites`.

### ADR-003 — Share-link target must belong to the same workspace; only `revoked_at` is mutable

**Context.** Links could target another workspace's task / board, readable by
anyone with the token (F-2026-10-01-01).

**Decision.**
- INSERT policy: `kind = 'task'` → target in `tasks` of the same workspace;
  `kind = 'board'` → target in `projects` of the same workspace; otherwise denied.
- UPDATE privilege only on `revoked_at`; policy requires `revoked_at is not null`
  (no un-revoke). Re-sharing = new link.
- `get_shared()` re-checks `workspace_id = link.workspace_id` (defence in depth)
  and returns only display fields.
- Tokens are 128-bit random, generated client-side with `crypto.getRandomValues`.

**Enforced in.** `…1840_scope_share_links_to_own_workspace.sql`.

### ADR-004 — Tenant / workspace ids are immutable in ordinary client updates

**Context.** Full-row UPDATE grants allowed moving projects / clients / rules /
notifications between workspaces (Free-plan limit bypass, F-2026-10-01-07).

**Decision.** Ordinary client updates use **column-level** UPDATE grants that
exclude `id`, `workspace_id`, parent ids and `created_at`:
projects (`name, description, color, gradient`), board_columns
(`status_key, label, wip_limit, position`), clients
(`project_id, name, email, hourly_rate, budget, report_day` + same-workspace
project check), automation_rules (`name, trigger, action, param, active, runs`),
notifications (`read_at`), share_links (`revoked_at`), comments (`body, liked_by`),
workspaces (`name`), profiles (`full_name`), workspace_members (`role, capacity`).
`tasks` keeps a full grant but `tasks_permission_check` rejects workspace changes
and cross-workspace project moves. `role_permissions` keeps a full grant because
the app upserts; its policies pin the row to the caller's workspace.

**Enforced in.** `15_api-grants`, `…1880`, `…1840`, `…1860`, `14_role-permissions` trigger.

### ADR-005 — Comment author, task and workspace identity are immutable

**Context.** Editors could rewrite others' comments or forge `author_id` (F-2026-10-01-05).

**Decision.** Only `body` and `liked_by` are updatable. Trigger
`comments_update_check`: `body` may change only when `auth.uid()` is the author;
`liked_by` may change only by adding / removing the caller's own id. INSERT
requires `author_id = auth.uid()`, task in the same workspace, and a reply's
parent on the same task and workspace.

**Consequences.** Concurrent likes with a stale list are rejected (COMMENT-LIKE-RACE-001).

**Enforced in.** `…1860`, `…1890`. **Verification:** trigger not yet fired by a real user (TEST-ROLE-001).

### ADR-006 — Service-role key usage restrictions

**Context.** `SUPABASE_SERVICE_ROLE_KEY` bypasses RLS.

**Decision.** Not used anywhere in `src` as of 2026-10-01 (code search). Any
future use needs explicit approval and must follow CLAUDE.md §5.5: server-only,
never `NEXT_PUBLIC_`, authenticate + authorize + verify workspace membership and
resource scope before every call, document each endpoint, filter output.
Planned uses (billing webhooks, background jobs) must each get their own ADR.

### ADR-007 — SECURITY DEFINER functions: least EXECUTE privilege

**Decision.** Trigger functions: no EXECUTE for `PUBLIC` / `anon` / `authenticated`.
RLS helpers and storage meter functions: `authenticated` + `service_role` only.
Only `get_shared(text)` is public by design. Functions that take a workspace id
and return tenant data must check `is_member()` inside (storage functions do).
Every migration that creates a function revokes `PUBLIC` / `anon` unless public.

**Enforced in.** `…1800`, `…1810`, `…1820`.
