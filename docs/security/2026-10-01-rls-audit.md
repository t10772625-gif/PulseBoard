## Findings

### F-2026-10-01-01 — Share links could expose another workspace's data

- **Severity:** High
- **Location:** `share_links` policies `share_links: create` / `share_links: revoke`; function `get_shared(text)`
- **Problem:** Creating a share link only checked the caller's rights on
  `workspace_id`, not that `target_id` (the task or board) belongs to that
  workspace. The creator could also `UPDATE target_id` later. `get_shared()`
  (SECURITY DEFINER, callable without signing in) returned whatever `target_id` pointed to.
- **Attack:** A user in Workspace A creates a link, sets `target_id` to the id of
  a task or board in Workspace B, then opens `/share/<token>` signed out → B's
  task title / description, or B's board name and all its task titles. Needs
  B's id (leaked URL, screenshot, email, former member).
- **Impact:** Cross-tenant data disclosure to unauthenticated visitors.
- **Fix** — [`20261001001840_scope_share_links_to_own_workspace.sql`](../../supabase/migrations/18_security-hardening/20261001001840_scope_share_links_to_own_workspace.sql), three layers:
  1. INSERT policy now requires the task / board to be in the link's workspace.
  2. UPDATE limited to the `revoked_at` column, and a revoked link cannot be un-revoked.
  3. `get_shared()` re-checks `workspace_id` on the task / board / tasks it returns, so even a bad row returns nothing.
- **Why this way:** defence in depth — the policy stops new bad rows, the
  column grant stops edits, and the function protects against any row that
  ever gets in some other way (e.g. service role). The app already only sends
  same-workspace ids and only updates `revoked_at`, so no app change was needed.

### F-2026-10-01-02 — Any user could be added to a stranger workspace

- **Severity:** High
- **Location:** `workspace_members` policy `members: add`; `profiles: read self and teammates`
- **Problem:** Anyone with `member.manage` could INSERT a membership for any user id, without that user's consent.
- **Attack:** Every new user is Owner of their own workspace. An attacker
  inserts `(their_workspace, victim_user_id, 'Viewer')`; the victim is now a
  "teammate", so the profiles policy lets the attacker read the victim's
  **email and name**. The victim may also suddenly see the attacker's workspace.
- **Impact:** Personal data disclosure; unwanted workspace membership.
- **Fix** — [`20261001001850_remove_direct_member_insert.sql`](../../supabase/migrations/18_security-hardening/20261001001850_remove_direct_member_insert.sql): policy dropped and INSERT privilege revoked.
- **Why this way:** the app never inserts members directly. People join through
  `workspace_invites`, and the sign-up trigger `handle_new_user()` (SECURITY
  DEFINER, owner `postgres`) adds the membership, so it is unaffected. Role
  changes and removals are unchanged.

### F-2026-10-01-03 — Storage functions leaked other workspaces' usage and plan

- **Severity:** Medium
- **Location:** functions `storage_used_bytes(uuid)`, `storage_limit_bytes(uuid)`
- **Problem:** SECURITY DEFINER and callable over `/rest/v1/rpc/…` by any role, for any workspace id.
- **Attack:** Call `storage_limit_bytes('<other workspace id>')` → learn its plan
  (free / pro / legendary); `storage_used_bytes` → its storage usage.
- **Impact:** Cross-tenant information disclosure (business data).
- **Fix** — [`…1800`](../../supabase/migrations/18_security-hardening/20261001001800_restrict_storage_quota_functions_to_members.sql):
  a signed-in caller only gets values for workspaces they belong to (otherwise
  `null`); server roles (no `auth.uid()`) still get values so the quota trigger
  keeps working. [`…1820`](../../supabase/migrations/18_security-hardening/20261001001820_revoke_anon_execute_on_rls_helpers.sql) removes `anon` / `PUBLIC` EXECUTE.
- **Why this way:** the app calls these over RPC for the Settings storage meter
  and the storage upload policy calls them, so they can't simply be revoked
  from `authenticated`. Same signatures → existing policy and trigger keep working.

### F-2026-10-01-04 — Email rate limit did not apply to Members

- **Severity:** Medium
- **Location:** `/api/email` ([`route.ts`](../../src/app/api/email/route.ts)); `email_outbox` SELECT policy
- **Problem:** The route counts the sender's emails in the last hour by reading
  `email_outbox`, but only admins could read that table. For Members the count
  was always 0. If the count query failed, the limit was also silently skipped.
- **Attack:** A Member sends unlimited emails through the app (spam to teammates, provider cost).
- **Impact:** Abuse / cost; violates the 50-per-hour rule.
- **Fix:** [`…1830`](../../supabase/migrations/18_security-hardening/20261001001830_allow_senders_read_own_email_outbox.sql)
  adds `email_outbox: senders read own` (a sender reads only rows they queued).
  `route.ts` now **fails closed**: if the count can't be read, no email is sent (HTTP 500).
- **Why this way:** smallest change that makes the existing limit work; senders
  see nothing new except their own send log. 500 (not 503) because the client
  treats 503 as "email not configured" and would hide the failure.

### F-2026-10-01-05 — Comments could be rewritten or forged by other users

- **Severity:** Medium
- **Location:** `comments` policy `comments: author updates` + full UPDATE grant
- **Problem:** Any editor could UPDATE any comment's `body`, `author_id`,
  `task_id`, `workspace_id` and `liked_by`.
- **Attack:** A Member edits an Admin's comment text, or sets `author_id` so a
  comment looks like someone else wrote it; or removes other people's likes.
- **Impact:** Integrity of discussion / audit trail.
- **Fix** — [`…1860`](../../supabase/migrations/18_security-hardening/20261001001860_protect_comment_authorship.sql):
  UPDATE limited to `body` and `liked_by`; trigger `comments_update_check`
  allows `body` changes only by the author, and `liked_by` changes only by
  adding / removing the caller's own id.
- **Why this way:** the app only updates `liked_by` (likes). A trigger is needed
  because RLS can't tell which column changed.
- **Side effect:** if two people like the same comment at the same moment, the
  second request (with a stale list) now fails instead of silently deleting the
  first person's like. Refresh and like again.

### F-2026-10-01-06 — Child rows could reference another workspace's task

- **Severity:** Low
- **Location:** INSERT policies on `comments`, `attachments`, `task_events`, `notifications`
- **Problem:** Policies checked rights on `workspace_id` but not that `task_id`
  (and a reply's `parent_id`) belong to the same workspace. `attachments.storage_path`
  was not tied to the workspace folder.
- **Attack:** Insert a row pointing at a guessed task id from another
  workspace; the foreign-key error vs success tells the attacker the id exists.
  No data is read back (SELECT policies use the row's own workspace).
- **Impact:** Bad cross-tenant references; task-id existence oracle.
- **Fix** — [`…1870`](../../supabase/migrations/18_security-hardening/20261001001870_check_task_workspace_on_child_inserts.sql)
  (attachments, task events, notifications) and [`…1860`](../../supabase/migrations/18_security-hardening/20261001001860_protect_comment_authorship.sql)
  (comments, reply parent): each INSERT policy = the previous one + "task is in
  this workspace". Attachments also require `storage_path` to start with `<workspace_id>/`
  (the app's upload path is `<workspace>/<task>/<file>`).

### F-2026-10-01-07 — Rows could be moved between workspaces (Free-plan limit bypass)

- **Severity:** Low
- **Location:** UPDATE grants on `projects`, `board_columns`, `clients`, `automation_rules`, `notifications`
- **Problem:** Every column was updatable, including `workspace_id` and parent ids.
- **Attack:** A user who manages two workspaces moves a project from a Pro
  workspace into a Free one — the 1-project limit trigger only runs on INSERT.
  Users could also re-point their own notifications at any workspace id; a
  client could be linked to another workspace's project.
- **Impact:** Plan-limit bypass; inconsistent tenant data.
- **Fix** — [`…1880`](../../supabase/migrations/18_security-hardening/20261001001880_lock_workspace_columns_on_update.sql):
  column-level UPDATE grants with only the editable columns; `clients: manage`
  requires a linked project to be in the same workspace.
- **Not changed:** `tasks` (the `tasks_permission_check` trigger already blocks
  moving tasks), `role_permissions` (the app upserts it and its policies pin the workspace).

### F-2026-10-01-08 — API returned raw database / provider errors

- **Severity:** Low
- **Location:** [`src/app/api/email/route.ts`](../../src/app/api/email/route.ts)
- **Problem:** Returned `qErr.message` (Postgres / RLS) and the Resend error
  message to the browser; a network failure to Resend threw an unhandled error
  and left the outbox row as `queued`.
- **Impact:** Internal details leaked (CLAUDE.md §6.1).
- **Fix:** Browser gets only `Forbidden` / `Operation could not be completed`.
  Server log gets safe metadata only (user / workspace / outbox id, error code
  — no email address, body or key). Provider message is still stored in
  `email_outbox.error`. Network failure marks the row `failed`.

### F-2026-10-01-09 — SECURITY DEFINER functions callable by anyone over RPC

- **Severity:** Low (reported by Supabase advisors, 13 functions × `anon` and `authenticated`)
- **Location:** trigger functions `handle_new_user`, `enforce_project_limit`,
  `enforce_storage_quota`, `check_task_update_permissions`; RLS helpers
  `member_role_in`, `is_member`, `can_edit`, `is_admin`, `has_permission`, `default_permission`
- **Problem:** Functions get EXECUTE for `PUBLIC` by default, and Supabase also grants `anon`.
- **Impact:** Low — trigger functions fail when called directly, and helpers only
  describe the caller's own role — but it widens the API surface for no reason.
- **Fix:** [`…1810`](../../supabase/migrations/18_security-hardening/20261001001810_revoke_execute_on_trigger_functions.sql)
  revokes EXECUTE on trigger functions from everyone (Postgres checks EXECUTE
  when a trigger is created, not when it fires).
  [`…1820`](../../supabase/migrations/18_security-hardening/20261001001820_revoke_anon_execute_on_rls_helpers.sql)
  revokes helpers from `anon` / `PUBLIC` and keeps `authenticated` (RLS policies need them).
- **Rule for new functions:** revoke `anon` / `PUBLIC` EXECUTE in the migration
  that creates a function, unless it is meant to be public.

### F-2026-10-01-14 — Regression: comment replies rejected (introduced by …1860)

- **Severity:** Medium (functional regression, not a security hole — it denies too much)
- **Location:** `comments` policy `comments: create`, as created by [`…1860`](../../supabase/migrations/18_security-hardening/20261001001860_protect_comment_authorship.sql)
- **Problem:** The reply check was written as
  `select 1 from public.comments pc where pc.id = parent_id …`. Inside that
  sub-query the unqualified `parent_id` resolves to the inner table
  (`pc.parent_id`), not the new row, so Postgres stored `pc.id = pc.parent_id`
  — never true. Every comment with a parent (a reply) is rejected; top-level
  comments work.
- **How it was found:** post-apply read of `pg_policies` (the stored expression
  shows the resolved column). The pre-apply SELECT test only proved the
  expression compiles, not which column it binds to.
- **Impact:** Replies failed with an RLS error between applying `…1860` and `…1890`.
  No data affected (0 comments existed).
- **Status:** VERIFIED FIXED AT DB LEVEL — BROWSER VERIFICATION PENDING. `…1890` applied 2026-10-01;
  stored policy expression corrected (`pc.id = comments.parent_id`) and DB scenario test passed; browser authenticated test pending.
- **Fix** — [`…1890`](../../supabase/migrations/18_security-hardening/20261001001890_fix_comment_reply_parent_check.sql):
  recreates the policy with every new-row column written as `comments.<column>`.
  The applied `…1860` file is left unchanged (applied migrations are not rewritten).
- **Lesson:** in policy sub-queries on the **same** table, always qualify the
  new row's columns with the table name; after applying, read the policy back
  from `pg_policies`.
